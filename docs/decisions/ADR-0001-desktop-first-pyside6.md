# ADR-0001: 1차 구현을 PySide6 데스크톱으로 한다

## 상태

채택 (2026-07-26)

## 문제

TECHSPEC §3은 Django + DRF + PostgreSQL + React 웹 서비스를 권장한다.
그러나 현재 필요한 것은 "판정 규칙이 실제로 쓸 만한가"를 빠르게 확인하는 것이지,
인증·배포·API 계약을 갖춘 서비스가 아니다.

웹 스택으로 시작하면 첫 진단 결과를 보기까지 인증, 마이그레이션, CORS,
빌드 파이프라인을 먼저 통과해야 한다. 이 과정에서 검증되는 것은 인프라이지 제품 가설이 아니다.

한편 최종 목표는 웹 서비스다. 데스크톱 코드가 웹에서 버려지면 손해다.

## 결정

1차는 PySide6 데스크톱 애플리케이션으로 만든다. 단, 다음 계층 분리를 강제한다.

```text
ui (PySide6)  →  services (AppService)  →  storage (SQLAlchemy)  →  core (순수 파이썬)
```

- `core`는 Qt, SQLAlchemy, 네트워크, 파일시스템에 의존하지 않는다.
  점수·신뢰도·피벗·보고서 생성이 전부 여기 있다.
- `services.AppService`는 UI와 무관한 파사드다. 웹으로 옮길 때 Django/FastAPI 뷰가
  이 메서드를 그대로 호출한다.
- `ui`에는 판단 로직을 두지 않는다. 화면 코드가 규칙을 재구현하면 UI와 분석 결과가 어긋난다.

저장소는 SQLite + SQLAlchemy 2.0 선언형 모델을 쓴다. UUID(문자열), JSON 컬럼,
timezone-aware datetime을 써서 PostgreSQL 이전 시 연결 문자열 외에는 바뀔 것이 거의 없게 한다.

## 대안

**A. 처음부터 Django + React**
- 장점: 재작업이 없다. TECHSPEC과 일치한다.
- 단점: 첫 진단 결과를 보기까지 걸리는 시간이 길다. 검증 대상이 아닌 것에 시간을 쓴다.

**B. CLI + Markdown 출력만**
- 장점: 가장 빠르다.
- 단점: 화면 B(구조화 검토)의 실시간 경고, 화면 D(후보 비교)처럼 이 제품의 핵심 상호작용을
  전혀 검증하지 못한다. 이 제품은 "표를 읽고 판단을 바꾸는" 도구라 UI가 곧 제품이다.

**C. 웹 프론트만 로컬 파일 기반으로**
- 장점: 나중에 그대로 재사용.
- 단점: 브라우저 저장소는 버전·감사 로그 관리에 부적합하고, 결국 백엔드를 만들어야 한다.

## 장점

- 첫 실행까지 `pip install` 하나면 된다. 배포·인증·CORS가 없다.
- `core`와 `services`가 웹 이전 시 그대로 재사용된다. 버려지는 것은 `ui`뿐이다.
- 계층 규칙이 테스트로 강제된다. `core` 테스트는 Qt 없이 돌아간다.

## 단점

- UI 코드(약 2,000줄)는 웹 이전 시 버려진다.
- 다중 사용자 동시 편집을 검증할 수 없다.
- 데스크톱에서는 권한 모델을 실제로 시험하기 어렵다.
  (그래도 `AppService._require_project`에서 소유자 검사를 하고 테스트도 둔다.
  웹 이전 시 그 검사가 그대로 권한 검사가 된다.)

## 영향

- `pyproject.toml` 의존성: PySide6, SQLAlchemy, jsonschema
- 테스트는 offscreen 플랫폼에서 UI 스모크까지 포함해 돌린다.
- TECHSPEC §3의 권장 스택은 Phase 5 이후 웹 전환 시점에 적용한다.

## 재검토 조건

다음 중 하나가 발생하면 웹 전환을 재검토한다.

- 사용자 2명 이상이 같은 프로젝트를 동시에 편집해야 할 때
- 분석을 다른 기기에서 이어서 봐야 할 때
- LLM 연동으로 API 키를 서버에 두어야 할 때
- 데스크톱 배포(코드 서명, 자동 업데이트) 비용이 웹 배포 비용을 넘을 때
