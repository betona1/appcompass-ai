# ADR-0003: LLM은 초안만 만들고, 판정에는 관여하지 않는다

## 상태

채택 (2026-07-26). ADR-0002의 재검토 조건이 충족되어 그 결정을 부분적으로 갱신한다.

## 문제

ADR-0002는 "사용자가 화면 B의 입력 부담 때문에 이탈하는 것이 확인될 때"를 재검토 조건으로 두었다.
그 조건이 충족되었다.

- 화면 B는 12개 칸을 요구한다. 그중 `첫 성공 경험`, `재방문 이유`, `대체 방법의 한계`처럼
  개념을 알아야 채울 수 있는 칸이 절반이다.
- 사용자는 v0.3.0 작업 중 "너무너무 어려운감이있어… 다음단계에 뭘할지 막막해"라고 보고했다.
- v0.3.0에서 튜토리얼과 다음 단계 안내를 붙였지만, 그것은 **무엇을 해야 하는지**를 알려 줄 뿐
  **무엇을 써야 하는지**의 부담은 그대로다.

동시에 CLAUDE.md §10.2와 ADR-0002의 마지막 문장은 그대로 유효하다.
LLM에 점수·신뢰도·피벗을 맡기면 이 제품의 존재 이유가 사라진다.

## 결정

LLM을 붙이되, **관여 범위를 초안 생성으로 한정**한다.
그 경계를 문서가 아니라 **코드 구조와 테스트**로 강제한다.

### 1. 관여하는 곳 (CLAUDE.md §10.1 허용 범위)

| 기능 | 화면 | Port |
|---|---|---|
| 원문 → 구조화 12칸 초안 | B. 구조화 검토 | `StructurerPort` |
| 언노운(확인이 필요한 것) 생성 | B (초안에 포함) | 〃 |
| 타깃 후보 초안 | D. 타깃 후보 | `TargetCandidatePort` |

`MvpPlannerPort`는 **구현하지 않는다.** MVP 범위는 도메인 모듈의 `constrain_mvp()`가
문서 근거로 제약하는 영역이고, 검증되지 않은 기능을 LLM이 추가하면
"측정 없는 추천 금지"(§2.6)가 무너진다.

### 2. 관여하지 않는 곳 — 구조로 막는다

문서로 금지하는 것만으로는 부족하다. 네 겹으로 막았다.

1. **반환 타입에 판정 필드가 없다.** `StructureDraft`, `TargetDraft`에는
   점수·신뢰도·피벗을 담을 자리 자체가 없다.
2. **출력 스키마가 `additionalProperties: false`다.** 모델이 `total_score`를
   끼워 넣으면 검증에서 떨어진다 (`test_schema_rejects_judgement_fields`).
3. **`run_analysis(assist=...)`는 분기에 쓰이지 않는다.** assist가 있든 없든
   점수·신뢰도·피벗·타깃·MVP가 완전히 동일함을 회귀 테스트로 고정했다
   (`test_llm_assist_does_not_change_judgement`).
4. **계층이 갈라져 있다.** `core`는 `llm`을 import하지 않는다.
   AST로 검사하는 테스트가 이를 지킨다 (`test_core_never_imports_the_llm_package`).
   `llm` 패키지를 통째로 지워도 분석 엔진은 그대로 돈다.

### 3. 초안은 승인 없이 어떤 칸도 덮어쓰지 않는다

`TECHSPEC F-020`의 "원문은 덮어쓰지 않는다"를 구조화 칸까지 확장한다.

- 초안 검토 창은 **모든 체크박스가 해제된 상태**로 열린다.
  '전부 적용' 버튼만 있으면 사용자는 읽지 않고 누른다.
- 각 칸에 `FROM_RAW_TEXT` / `INFERRED` / `MISSING` 근거를 표시한다.
  추측한 칸은 색으로 구분하고, '원문에 있는 칸만 선택' 버튼에서 제외한다.
- 이미 값이 있는 칸은 현재값과 초안을 좌우로 나란히 보여 준다.
- 채택한 칸 목록은 `ProjectVersion.llm_assist`에 남고 보고서에 표기된다.

### 4. 프롬프트 인젝션

사용자 원문은 시스템 프롬프트에 절대 들어가지 않는다.
`<사용자_원문>` 태그로 감싼 user 턴 데이터로만 들어가고, 시스템 프롬프트는
그 안의 명령형 문장을 "구조화할 내용"으로 취급하라고 명시한다.
원문에 태그 문자열이 있으면 제거해 구간이 조기 종료되지 않게 한다.

### 5. 스키마 실패 (CLAUDE.md §10.3)

```
1차 호출 → 검증 실패 → 1회 자동 복구 프롬프트 → 재검증 실패 → 초안 폐기
```

두 번 실패하면 **버린다**. 깨진 응답에서 쓸 만한 칸만 골라 쓰는 경로는 만들지 않는다.
그런 경로가 있으면 결국 검증되지 않은 값이 화면에 올라온다.

### 6. 키 관리

- 읽는 곳: 환경변수 `ANTHROPIC_API_KEY` → `.env` 파일 (환경변수 우선)
- **DB에 저장하지 않는다.** 기획서를 내보내거나 백업할 때 키가 딸려 나가는 사고를
  구조적으로 막는다.
- 화면·로그에는 마스킹된 값만 나온다 (`sk-ant-…abcd`).

## 대안

**A. 초안을 자동으로 채우고 사용자가 지우게 한다**
- 장점: 클릭이 줄어든다.
- 단점: ADR-0002가 지적한 바로 그 문제 — 사용자가 초안을 검토가 아니라 정답으로 취급한다.
  특히 `기대 결과`처럼 숫자가 들어가는 칸에서 그럴듯한 추측이 그대로 남으면
  이후 모든 진단이 그 추측 위에서 돌아간다.

**B. LLM으로 보고서 문장만 다듬는다**
- 장점: 판정 경계가 명확하다.
- 단점: 입력 부담이라는 실제 문제를 해결하지 못한다.
  보고서 문장이 딱딱한 것은 불만이 제기된 적 없다.

**C. LLM 없이 화면 B의 칸을 줄인다**
- 장점: 의존성이 늘지 않는다.
- 단점: 줄일 수 있는 칸이 없다. 12칸은 CLAUDE.md §2.1~2.6의 진단 항목과
  1:1로 대응하며, 빼면 해당 평가 항목을 채점할 수 없다.

## 장점

- 입력 부담이 실제로 줄어든다 — 가장 어려운 칸을 초안에서 시작할 수 있다.
- 판정 회귀 테스트는 그대로 유효하다. LLM이 붙어도 같은 입력에 같은 판정이 나온다.
- 키가 없어도 앱의 모든 기능이 그대로 동작한다. LLM은 순수한 추가분이다.

## 단점

- 의존성이 늘었다 (`anthropic`, `httpx`, `pydantic`). 실행파일 용량이 커진다.
- 사용자가 API 비용을 부담한다. 이 앱은 결제에 관여하지 않는다.
- 초안 품질은 검증할 수 없다. 그래서 채택을 사용자에게 맡기고, 근거를 함께 표시한다.
- 네트워크가 없으면 초안 기능만 꺼진다 (나머지는 정상).

## 영향

- `AnalysisMeta.engine`은 여전히 `RULE_ENGINE`이다.
  `model_name`은 "초안 도움 모델"이며, 보고서가 그 구분을 명시한다.
- `ProjectVersion`에 `llm_assist` 컬럼이 추가되었다.
  기존 DB는 `storage/migrations.py`가 앱 시작 시 컬럼만 더한다.
- 새 화면 'AI 도우미'가 역할 경계를 사용자에게 직접 알린다.

## 재검토 조건

- 초안 품질이 낮아 사용자가 결국 전부 다시 쓴다는 것이 확인될 때
  (→ 프롬프트를 고치고 `PROMPT_VERSION`을 올린다. 기록이 남아 비교할 수 있다)
- 스키마 실패율이 높을 때 (→ 스키마를 단순화하거나 모델을 바꾼다)
- 사용자가 추측(INFERRED) 칸을 그대로 채택하는 비율이 높을 때
  (→ 추측 칸을 아예 제안하지 않는 쪽으로 좁힌다)

**어떤 경우에도 점수 계산, 신뢰도 계산, 피벗 상태 결정은 LLM에 위임하지 않는다.**
ADR-0002의 이 문장은 갱신되지 않는다.
