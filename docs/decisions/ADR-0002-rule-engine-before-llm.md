# ADR-0002: LLM 없이 규칙 엔진만으로 Phase 1을 완주한다

## 상태

채택 (2026-07-26)

## 문제

TECHSPEC §9.1의 파이프라인은 아이디어 구조화, 타깃 후보 생성, 보고서 문장 작성에 LLM을 쓴다.
하지만 CLAUDE.md §10.2는 LLM이 점수를 계산하거나 피벗 상태를 결정하는 것을 금지한다.

즉 이 제품의 판정 정확도는 LLM이 아니라 **규칙 엔진과 정책값**이 결정한다.
LLM을 먼저 붙이면 다음 문제가 생긴다.

- 판정이 틀렸을 때 원인이 규칙인지 프롬프트인지 구분되지 않는다.
- 회귀 테스트가 불가능하다. 같은 입력에 같은 출력이 나오지 않는다.
- 그럴듯한 문장 때문에 규칙의 결함이 가려진다.

## 결정

Phase 1에서는 LLM을 전혀 호출하지 않는다. 대신 다음 세 가지를 갖춘다.

1. **구조화는 사람이 한다.** 화면 A에서 원문을 받고, 화면 B에서 사용자가 직접
   구조화 필드를 채운다. 규칙 엔진이 입력 중에 실시간으로 경고를 보여준다.
   자동 해석 초안은 만들지 않는다 — 품질이 낮은 초안은 사용자의 판단을 오염시킨다.

2. **타깃 후보와 MVP는 도메인 지식에서 나온다.** 도메인 모듈이
   `seed_target_candidates()` / `constrain_mvp()`로 문서 근거가 있는 후보와 제약을 제공한다.
   근거가 부족하면 추천하지 않고 비교만 제공한다.

3. **LLM 자리는 인터페이스로 비워 둔다.** `core/ports.py`에
   `StructurerPort` / `TargetCandidatePort` / `MvpPlannerPort` Protocol을 정의한다.
   `AnalysisMeta`에 `model_provider` / `model_name` / `prompt_version` 필드가 이미 있고,
   보고서에도 이미 출력된다. 지금은 "사용 안 함 (규칙 엔진 전용)"으로 표시된다.

모든 분석 결과는 저장 전에 `schemas/analysis_result-0.1.0.json` 검증을 통과해야 한다.
지금은 규칙 엔진 출력만 통과하지만, LLM을 붙였을 때 "검증 없이 저장"하는 경로가
애초에 존재하지 않도록 하기 위해서다.

## 대안

**A. 처음부터 LLM으로 구조화**
- 장점: 사용자 입력 부담이 적다.
- 단점: 판정 결함과 프롬프트 결함이 섞인다. 회귀 테스트가 불가능하다.
  API 키 관리·비용·지연·실패 처리가 Phase 1 범위를 넘긴다.

**B. 휴리스틱 파서로 구조화 초안 자동 생성**
- 장점: 입력 부담이 줄어든다.
- 단점: 한국어 자유 문장에서 "핵심 행동"과 "기대 결과"를 규칙으로 분리하는 것은
  신뢰할 만한 수준이 되지 않는다. 틀린 초안은 빈 칸보다 나쁘다 —
  사용자가 초안을 검토가 아니라 정답으로 취급한다.

## 장점

- 두 도메인 고정 시나리오(TECHSPEC §15.3)를 회귀 테스트로 고정할 수 있다.
- 판정이 이상하면 원인이 규칙 하나로 특정된다.
- API 키, 비용, 지연, 스키마 실패 복구가 Phase 1에 없다.
- 사용자가 직접 필드를 채우는 과정 자체가 CLAUDE.md §2.1이 요구하는 사고 훈련이다.

## 단점

- 입력 부담이 크다. 12개 필드를 사람이 채워야 한다.
- 보고서 문장이 템플릿이라 딱딱하다.
- 타깃 후보가 도메인 모듈에 하드코딩된 것 + 현재 입력 파생분으로 제한된다.
  새 도메인에는 후보가 없다(이 경우 후보를 제시하지 않고 그 사실을 명시한다).

## 영향

- `core/ports.py`의 Protocol은 구현체 없이 존재한다.
- `AnalysisMeta.engine = "RULE_ENGINE"`, `model_name = None`.
- 회귀 테스트 `test_same_input_same_output`이 재현성을 강제한다.

## 재검토 조건

- 사용자가 화면 B의 입력 부담 때문에 이탈하는 것이 확인될 때
  (→ `StructurerPort` 구현체를 붙이되, 결과는 여전히 '초안'이며 승인 전 반영하지 않는다)
- 규칙 기반 타깃 후보가 도메인 밖 프로젝트에서 쓸모없다는 것이 확인될 때
- 보고서 문장 품질에 대한 불만이 반복될 때 (→ 문장 생성만 LLM, 값은 규칙 엔진 그대로)

**어떤 경우에도 점수 계산, 신뢰도 계산, 피벗 상태 결정은 LLM에 위임하지 않는다.**
